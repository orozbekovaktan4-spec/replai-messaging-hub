## Context

**Manager's Investigation Findings:**

The user reports Telegram "works", but evidence shows:

1. ✅ **Token exists**: `TELEGRAM_BOT_TOKEN` is configured in `.env` (treat as **compromised** - exposed in conversation)
2. ❌ **Connection state**: `connections.json` shows `"connected": false`
3. ❓ **Webhook status**: Unknown if webhook is registered with Telegram API
4. ❓ **Message flow**: No evidence of real messages in production database
5. ⚠️ **Dual state system**: Two competing connection status implementations:
   - **In-memory**: `platformConnections.telegram` (line 542-565 in `server-new.js`) - initialized from `process.env.TELEGRAM_BOT_TOKEN`
   - **Persistent**: `connections.json` managed by `connection-manager.js`

**Root Cause Hypothesis:**

The in-memory `platformConnections` object loads the token from `.env` on server startup and considers Telegram "connected" if the token exists. However, `connections.json` shows `connected: false` because:

- Either the connection was never properly established through the connection manager
- Or the webhook was never registered with Telegram
- Or the token is invalid/expired but the server doesn't know

**Security Alert:**

The current bot token in `.env` was accidentally exposed in a previous conversation. It must be treated as compromised. Never print or expose token values.

   - Modify `/api/admin/telegram/connect` (line 2271) to ensure both states are updated
   - After successful `connector.connect(token)`, update `platformConnections.telegram`
   - Ensure disconnect also updates both
   
   **Option B - Make connection-manager the single source of truth:**
   - Modify `platformConnections` initialization to read from `connections.json`
   - Remove direct environment variable reading for connection status
